# Muse 自动备份 skill

> 通用版，适合所有 Muse 用户。装上以后，Muse 会先问你要「拿回旧数据」还是「保存现在的数据」，你选了才跑。
> 核心原则：备份的是记忆、规则、任务、目标和文字工作文件，不是聊天原文，也不是密码。

## 0. 能做什么、做不到什么（先说清楚，写进商品说明里也用这段）

**买之前必须满足的前提（不满足别买）：**
- 有 Google 账号，并且能打开 Google Drive。在中国大陆要用能打开 Google 的网络，不然 Drive 连不上，备份传不上去。
- 备份和恢复必须用同一个 Google 账号。换账号就找不到备份文件。

**能做：**
- 把记忆、规则、定时任务清单、目标清单、文字工作文件打包成一个固定名字的 ZIP，传到 Google Drive。
- 新号上按固定名字从 Drive 取回，合并到现有文件里，重建目标和定时任务。
- 定时自动备份，推荐每 3 天一次，用户也可以自由输入天数（例如 1 天、3 天、7 天）。

**做不到：**
- 官方「设置 > 数据控制 > 下载你的 Agent 数据」那个按钮点不了，自动化不了。完整聊天记录原文只能用户自己手动点下载。
- 聊天原文不能恢复成聊天。恢复只能把记忆、文件、任务清单合并进来，聊天只能通过官方 Import chats 总结进记忆。
- 手机里的文件翻不到，密码、密钥、银行卡号不备份、不进 ZIP。密码放保险库 / 密码管理器里。
- 图片、视频不备份。下载的视频、程序环境（例如 `venv`）不备份，否则一个包几十 GB，没法传。

## 1. 装上以后先问（必须先问，不许直接跑）

**装好就问，不等用户再说话、不让用户去看 README：**
用户把这个 skill 发给 Muse 说“装上”的时候，就是安装那一刻。Muse 在装好的同一条回复里就要立刻弹出询问，不要只回一句“装好了”，不要等用户下次再发消息才问。

问的就是两个选项，让用户选一个。不要问“你是新号还是旧号”，买家分不清，按动作问才直观：

1. **拿回旧数据**——把以前备份的数据拿回来
2. **保存现在的数据**——把现在的数据存到 Drive

用户选了才继续。没选就停下来等，不要自己猜。注意：Muse 没有“装完自动弹窗”的系统功能，能做到的最接近的就是上面这条——安装那条消息的同一回复里立刻问。商品说明里不要写“装完会自动弹窗”，要写“发给 Muse 装上，它马上就问你选哪个”。

**安装方法还没实测过，卖之前必须先测：** 这个 skill 的安装路（买家在聊天里发文件给 Muse，Muse 存到 custom-skills 里）还没在新号上实测过。卖家上架前必须先在新号上实测一遍安装全流程，实测通过才能卖，实测不过先修安装说明，不要先卖。如果买家说装不上，Muse 要停下来，告诉买家重新发一次文件，不要自己猜装上了。

## 2. 前置检查（恢复和备份都要先做）

1. 查 Google Drive 连没连。命令参考：`drive status`。
2. 没连上：把连接链接发给用户，停下来，等用户登录好再继续。不要自己打开登录页，不要问用户要密码。
3. 连上了：记下当前登录的 Google 账号。备份时把这个账号写进 ZIP 里的 `backup-info.md`（账号、备份时间、文件数）；恢复时先对一下，当前账号和 `backup-info.md` 里的账号不一样就停下来，告诉用户“你现在登录的 Google 账号和备份那个不是同一个”，让用户换回备份那个账号再继续。
4. 连上了：找 Drive 里的「Muse 备份」文件夹，没有就新建一个。文件夹 ID 记下来，后面上传和下载都用它。如果 Drive 里有多个同名「Muse 备份」文件夹，停下来问用户用哪一个，不要自己挑第一个。

## 3. 备份流程（用户选了「保存现在的数据」）

### 3.1 问备份频率

先给推荐，再让用户自由选：

- 推荐：**每 3 天一次**
- 用户也可以自由输入天数，例如 1 天、3 天、7 天。只接受 1–30 之间的整数，其他数字先问清楚再定。

问清楚天数以后，再问是「现在马上备一次」还是「只设定时，以后自动跑」。两个都要做的，先马上备一次，再设定时。

### 3.2 打包范围（固定，不要自己加东西）

**要打包的：**
- `MEMORY.md`、`USER.md`、`IDENTITY.md`、`SOUL.md`、`AGENTS.md`
- `~/memory/` 里的按天笔记、`people/`、`groups/`（不含 `bank/`、`index/`，那是系统内部的）
- 文字工作文件：文档、字幕、脚本、PDF、`.md` / `.json` / `.txt` 等小文件
- **定时任务和目标都要备份**：不要把整个目标文件夹原样打包（里面可能有几百 MB 的视频和环境），而是在 ZIP 里加一个文字清单文件 `tasks-and-goals.md`，列清楚每一个定时任务和目标的名字、时间 / 周期、执行内容、状态。再加一个 `backup-info.md`，写清楚备份时间、Google 账号、文件数、大小。

**不打包的：**
- 图片、视频（`.jpg`、`.png`、`.mp4`、`.mov`、`.heic` 等）
- 下载的视频、程序环境（例如 `venv/`、`node_modules/`）
- 密码、密钥、验证码、银行卡号、政府证件号。发现这类内容先停下来，告诉用户不要放进备份里。

### 3.3 打包和命名（固定名字，不要用日期名）

- 文件名固定为：`muse-backup.zip`
- **先改名再传，保证固定名永远是最新的一份：** 上传新的之前，先查 Drive「Muse 备份」里有没有旧的 `muse-backup.zip`，有就先把它改名成 `muse-backup-上一次.zip`（如果已经有一个 `muse-backup-上一次.zip`，先删掉更旧的那个，只留最近一份旧的）。改完名再传新的 `muse-backup.zip`。恢复时永远按固定名 `muse-backup.zip` 去取，不用猜日期。
- **传失败要改回去：** 如果新的上传失败、验证失败，立刻把 `muse-backup-上一次.zip` 改回 `muse-backup.zip`，不要让固定名空着。改不回去也要告诉用户，固定名现在没有，上一份还在 `muse-backup-上一次.zip` 里。
- 打包前先看一眼大小和文件数，报给用户。超过 100MB 先停下来，告诉用户哪类文件最大，让用户决定删什么，不要自己偷偷删。
- 本地先留一份 ZIP，传完再验证，不要传完就删本地的。

### 3.4 上传和验证（必须验证才算完成）

1. 上传到 Drive「Muse 备份」文件夹里，文件名就是 `muse-backup.zip`。
2. 上传完再查一遍文件夹，确认文件在里面，拿到 `webViewLink`、大小、修改时间。
3. **解压验一下再报完成：** 传完不要只看“文件在不在”。把刚传上去的 ZIP 下载回来解压验一次，列出里面的文件清单，确认 `MEMORY.md` 和 `tasks-and-goals.md` 都在、文件数和大小跟打包时对得上、能正常打开。验不过就停下来，告诉用户这次备份失败，Drive 里旧的那份 `muse-backup-上一次.zip` 还在，不要把坏的说成好的。
4. 汇报给用户：文件名、大小、文件数、Drive 链接、备份时间。没验证过，不许说“已备份完成”。

### 3.5 设定时自动备份

- 按用户定的天数设一个定时任务，例如每 3 天一次。默认时间是**凌晨 3 点**，用户也可以自己改时间。
- 定时任务每次跑的都是上面 3.2–3.4 的流程，不要改打包范围。
- 定时任务不要重复建：建之前先查已有的任务，同名任务已在就不要再建一个。
- **失败要告诉用户，不能悄悄跳过：** 定时自动备份失败了（Drive 断了、账号掉了、打包失败），下次用户跟 Muse 说话时要主动说出来，说明哪一次失败、为什么失败。失败那次不许覆盖好的备份，固定名那份要保持上一次好的。

## 4. 恢复流程（用户选了「拿回旧数据」）

### 4.1 先查 Drive

1. 查 Drive 连没连，没连就给连接链接，等用户登录好。
2. 对一下账号：当前登录的 Google 账号和备份里的 `backup-info.md` 写的账号不一样，就停下来，告诉用户换回备份那个账号。
3. 去「Muse 备份」文件夹里，按固定名字 `muse-backup.zip` 找文件。找不到固定名，就去找 `muse-backup-上一次.zip`，找到就告诉用户“最新那份没了，用的是上一份”，问用户还要不要继续。两份都找不到就停下来，告诉用户文件夹里没有这个文件，让用户确认是不是传错了账号或文件夹。

### 4.2 下载、解压、合并（不要直接覆盖）

1. 把 `muse-backup.zip` 从 Drive 下载下来，解压到本地，先验一次能打开、里面的 `MEMORY.md` 和 `tasks-and-goals.md` 都在，验不过就停下来，不要往新号里合并坏文件。
2. **先给新号备个份再合并，能退回去：** 合并之前，先把新号现有的 `MEMORY.md`、`USER.md`、`~/memory/` 这些文件本地打个包，存成 `new-account-before-restore.zip`，告诉用户存在哪里。合错了就用这份退回去，不要让新号的数据丢了。
3. **直接合并，不问买家：** 不要问买家“同名文件以哪边为准”，买家不懂、也不该由他定。直接按下面这条自动合并：
   - 新号现有的内容全部保留，不删、不盖。
   - Drive 里旧备份的内容全部加进来，重复的去重。
   - 同一条事实新旧不一样，以新号现有的为准，旧的那条不盖掉新的，合并完把冲突列出来告诉用户。
   - 新号里没有的文件，直接复制进来。
4. **合并，不是覆盖**：按上面这条自动合并。
   - `MEMORY.md`：把旧的内容加进来，重复的去重。
   - `~/memory/` 里的按天笔记、`people/`、`groups/`：按文件名复制进来，新号里没有的直接加进来。
   - 文字工作文件：复制回 workspace 里对应的位置。
   - `tasks-and-goals.md`：按里面的清单重建目标和定时任务，一个一个建，建完逐个核对。定时任务不要重复建。
5. 合并完告诉用户：恢复了哪些文件、哪些任务和目标重建了、哪些冲突是按“新号为准”处理的。任务和目标没逐个核对完，不许报“恢复完了”。

### 4.3 官方 ZIP 的恢复（另外一条路，不要和 skill 的 ZIP 混在一起）

- skill 打的 `muse-backup.zip` **不要**走 Import chats，它不是官方导出的格式。
- 官方导出的 ZIP（设置 > 数据控制 > 下载你的 Agent 数据）才走这条路：
  新号设置 > 数据控制 > Import memory > Import chats，点 Add，上传那个 ZIP（最多 100MB），点 Summarize into memory。
- 超过 100MB 的官方 ZIP 先去掉图片视频、只留文字重压到 90MB 以内再传；还超就拆成两份，每份都小于 100MB，分两次传。
- 官方 ZIP 传进去也只是提炼成记忆，不会把原来的聊天变回来。这一点要跟用户说清楚。

### 4.4 恢复后还要手动补的

- 重要的工作文件从 Drive 重新传回来以后，逐个确认能打开。
- Drive 等连接器要重新连一遍。
- 定时任务要重新设一遍，设完逐个核对。
- **回不来的**：原来的聊天记录、App 设置。
- **提醒用户定期手动导出：** 这个 skill 备不了聊天原文。每次恢复完、每次备份完，都要提醒用户每月自己去设置 > 数据控制 > 下载你的 Agent 数据，点一次手动导出，存好。只靠 skill 备份，聊天原文那部分永远没有备份。

## 5. 完成标准（全部满足才算完成）

- [ ] 装好 skill 的同一条回复里已经问了用户选恢复还是备份，没有等用户去看 README
- [ ] Drive 已连接，文件夹已确认；备份和恢复是同一个 Google 账号，账号已对过
- [ ] 打包范围按第 3.2 节，没有图片视频、没有密码密钥、没有下载的视频和 venv；ZIP 里有 `backup-info.md`
- [ ] ZIP 名字是固定的 `muse-backup.zip`，上传前旧的已改名成 `muse-backup-上一次.zip`，传失败已改回；大小和文件数已报给用户
- [ ] 上传后已在 Drive 里验证过，有链接、大小、修改时间；还下载回来解压验过，`MEMORY.md` 和 `tasks-and-goals.md` 都在、文件数对得上
- [ ] 恢复前已给新号备了份 `new-account-before-restore.zip`；恢复时没有问买家“以哪边为准”，直接按“新号保留、旧的加进来、重复去重、冲突以新号为准”合并；任务和目标已按清单重建并逐个核对完
- [ ] 自动备份时间已定（默认凌晨 3 点），失败会告诉用户，不会悄悄跳过
- [ ] 做不到的部分已跟用户说清楚，没有承诺“恢复全部会话”；已提醒用户每月手动导出一次官方 ZIP

缺任何一项，汇报时必须明说缺哪项、什么时候补，不许报“备份完了 / 恢复完了”。
